Capture keeps source records, drafts and save receipts in its shared SQLite database. Prepared media and transfer state are separate files. A record count or database size does not establish the size of those files.

Capture's storage must be measured before removing existing data. Saved and queued items, canceled or uncertain saves, deleted-but-restorable drafts, recordings, source media and evidence remain protected. A file with no observed record reference is a candidate for investigation, not permission to delete it. A directory named `Caches` is not sufficient evidence that its contents can be regenerated.

The October 16 device investigation exposed 30,664,855 logical bytes through CoreDevice: 10,850,835 bytes of older diagnostic evidence, 15,925,344 bytes of iOS screen snapshots, 2,416,544 bytes under OS cache paths, 1,466,352 bytes of HTTP storage and 5,780 other bytes. This is a partial listing. The app-group service did not expose the actual shared database or media directories listed in the app's own earlier diagnostic manifest. These measurements do not account for the user's reported almost 3 GB, and are not an allocated-storage total from Settings.

The existing redacted diagnostic snapshot was created on October 15 at 16:32:53 UTC. It contains 563 saved drafts, 13 queued/checking saves and local media references. Its database file is 10,817,536 bytes. These are historical counts; they do not establish the current queue, current media sizes, or which unreferenced files can safely be removed. Interrupted media preparation is a confirmed accumulation risk in the previous code, but its contribution to the phone's reported usage remains unmeasured.

New media preparation uses an explicitly owned `temporary-media-v1` workspace. Working downloads remain separate from durable render output. An OS file lock protects active app/Share preparation and open composition previews. Ordinary failure, cancellation and releasing a preview remove only that operation's working files. A finished upload body moves to `renders` before the durable save journal can reference it; temporary workspace paths are rejected by the queue intake. Stale, marked, flat workspaces with no live lock expire after 24 hours, or oldest first when inactive working copies exceed 250 MiB. Sweeping occurs on normal session startup and before new preparation. Active owners and unknown entries are excluded from those bounds. Legacy renders, previews, recordings and evidence are outside this cleanup policy.

An internal `CAPTURE_STORAGE_AUDIT_ONLY=1` launch mode bypasses `CaptureSession`, delivery initialization and background recovery. It enumerates the real main/shared containers and reads existing record references using a read-only SQLite connection. It exports metadata, byte counts, record-kind counts and classification problems to a new UUID-named JSON file under `Documents/CaptureStorageAudit`. It does not include authored source text or credentials, and does not clean up or resume saves. The exported report distinguishes logical bytes from available per-file allocated sizes; that sum need not equal iOS Settings' storage attribution.

Unsigned simulator builds may lack app-group registration. The Debug/simulator-only `CAPTURE_STORAGE_AUDIT_FIXTURE=1` switch selects a fixed synthetic directory inside that isolated app's own container. Its measured fixture sizes and queue-preservation checks qualify the diagnostic code, not the phone's current usage.

This mode requires a build that contains it. It is not present in the phone's installed Capture 20261016.4 or the frozen signed .5 artifact. No phone update, launch, cleanup or removal was performed during the initial investigation. Main merge and browser activation remain held.

Do not launch the installed .4 or frozen .5 with the audit flag: those versions ignore it and initialize normal capture recovery. Qualify and verify a build containing the guarded audit entry point before a phone diagnostic launch. The read-only mode has been exercised with synthetic queued records in an isolated simulator; a physical phone audit has not yet run.

Before any existing-data remediation, obtain a current complete shared-container inventory and a consistent current record/reference snapshot without resuming work. Check app/Share execution, URLSession transfers and every retained record kind, including pending, canceled, uncertain, saved and deleted-but-restorable captures. Produce an exact path/size/hash manifest and identify each candidate's producing code and lifecycle. Preserve the dependency closure, unknown files and all source/evidence files. Present the candidate set and measured reclaimable bytes for approval before removing existing phone data. Do not delete/offload Capture or bulk-resume saves to make space.
